# Architecture and persistence

## Loader separation

The loader-neutral economy and Village Prosperity simulation live in `common/src/main/java`. Shared Minecraft-facing menus, commands, inventory helpers, Banker access, village-bank generation, settlement observation, construction, and transaction reconciliation live in `common/src/minecraft/java`. Shared client screens live in `common/src/client/java`.

Fabric and NeoForge provide lifecycle hooks, menu registration, interaction and villager-death events, player connection hooks, metadata, and build configuration. Both loaders call the same economy and settlement services.

## Player interaction

Managed Banker villagers are persistent vanilla villagers carrying The Emerald Standard Banker tags and the registered `the_emerald_standard:banker` profession. Its workstation and acquirable point of interest use the dedicated `the_emerald_standard:exchange_desk` block. Right-clicking a managed or naturally employed Banker, or any Exchange Desk, opens a custom `BankerMenu`; unscoped access resolves the nearest managed settlement in the same dimension, while legacy bank lecterns remain valid only at persisted bank locations. All financial and Prosperity Fund actions execute server-side against `EconomyService`; the client never owns balances, prices, settlement state, drafts, confirmations, or transaction outcomes.

The eight dashboard pages are Account, Market, Banking, Trade, Village, Fund, Activity, and News. The menu synchronizes bounded account, portfolio-analytics, five-entry ledger windows, market, commodity-history, donor, and local-village snapshots rather than exposing the complete world-account map or private economy seed. Trade renders the canonical vanilla resource item beside an emerald without adding a new authority path. News is a deterministic client presentation over the existing synchronized village facts: a shared pure policy selects its headline, item visual, article, and prosperity/safety guidance, with no external generation service, extra world mutation, or invented incident. Activity paging accepts only one-step newer/older requests through the player's current server menu, clamps every offset to that player's retained 256-entry ledger, and synchronizes the window, total, and position; reconnecting starts at the newest entry. Irreversible or risky actions use a time-limited server-owned two-step confirmation, and the exact Fund contribution selection is maintained and bounded by the server.

Minecraft's container-data packet carries signed 16-bit values. The Banker therefore maps every logical 32-bit menu value to two signed-short wire limbs and masks both limbs when reassembling them. Existing 64-bit monetary values retain their low/high logical integers and consequently use four wire limbs. Both loaders share this packing boundary, and their dedicated-server self-tests exercise the real Minecraft packet codec at signed, unsigned, balance, Fund-draft, identifier, and 64-bit boundaries.

## Village banks and stable settlement identity

`VillageBankManager` remains responsible for the compact Village Bank and Exchange. `VillageProsperityManager` separately observes and materializes the local settlement economy.

A settlement receives a persistent UUID. Resolution uses, in order:

1. A persisted village identity already carried by observed residents when its dimension and location remain plausible.
2. An existing persisted bank-region association when it still matches the settlement and dimension.
3. A nearby existing settlement within a deliberately tighter proximity threshold.
4. A deterministic new identity.

The observed settlement center prefers the nearest loaded village bell and falls back to the villager cluster. Once a record is created, its persisted center remains the stable reference point. A player's location only triggers Bank discovery; after settlement resolution, Bank keying and deterministic plot selection use that stable center.

Village Banks remain an Overworld-only gameplay surface in the current beta. Existing coarse grid keys and their anchors remain valid for upgraded saves. If a new stable settlement shares an already-owned legacy grid, it receives a deterministic per-village bank key rather than borrowing or duplicating the other settlement's bank. That scoped key is carried through Banker replacement, menu lookup, and Fund mutation so proximity cannot silently redirect an action to the wrong nearby village. A generated Bank persists one canonical Banker UUID and its last durably assigned anchor. An unloaded UUID is retained rather than treated as death, so a chunk boundary cannot create a second scoped villager. A death callback only stages an observation; a later tick must observe the entity actually removed and complete an entity-inclusive Minecraft save before format 17 records replacement authority. Shutdown drains this ordering before runtime state is cleared. Minecraft 26.2 infection and cure use new entity UUIDs, so conversion first persists an exact root/source/target `PREPARED` transaction. Only after an all-active-level entity save and post-save participant revalidation can a typed durable phase commit a live target, a live immediate source, a live root, or retirement. Exact predecessor-lineage tags corroborate loaded entities but do not replace durable authority. A restart cannot promote `PREPARED` merely because its target is loaded: a predecessor could have rolled back in an unloaded chunk, so the transaction remains fail-closed until new positive lifecycle proof exists. An abrupt crash in a short cross-file boundary after Minecraft saves a conversion/removal but before format 17 records its durable phase—including an ordinary canonical-death handoff—can therefore lock the Bank until an exact participant later supplies a positive lifecycle event; the beta recovery is restoration from a pre-crash backup if no such event arrives. This liveness limitation is not the stable-release target. Chained conversions retain the original root and immediate source, terminal Witch outcomes retire the lineage, and ambiguity never chooses a successor. Scoped Banker interaction also requires the Overworld and proximity to the persisted assigned anchor, containing any cross-dimension duplicate UUID. A loaded Banker still near its prior managed site is moved and rebound to the replacement, then its entity is saved before the new assignment is committed. A Banker near neither managed site is treated as deliberately player-moved and is not forcibly teleported.

The current 13x11 Bank blueprint is authored structure version 5. Its north entrance has a three-block-wide landing and top stair; deterministic profiles for all three lanes must agree before the bounded natural approach adds equally wide descending rows. This rejects cross-slopes that would leave one lane afloat. Negative-Y stair columns receive support only beneath their lowest authored cell, preserving walkable headroom, while the shared foundation planner can bridge as much as four blocks of natural surface variation elsewhere on an otherwise safe lot. Front, rear, and transom panes carry east/west connections, while side-wall panes carry north/south connections; a live same-block normalization pass corrects surviving panes whose neighbor-derived state was lost during older structure placement. Version 5 retains the complete version-4 interior, two-wide secure alcove, three-wide entrance, Desk sightline, and supported lighting plan, then adds a full-backed front dormer, glazed bell cupola, articulated ridge, deep lobby-window bays, paved forecourt wings, and a rear ledger pediment. Its additional civic wall, pier, plinth, cornice, ledger, forecourt, and crown materials are v5-only, so stronger Desert, Savanna, Taiga, Snowy, and Plains identities cannot reinterpret an older structure. New and safely relocated replacement Banks use version 5. Intact version-2, version-3, and version-4 Banks remain independently frozen compatibility structures: each is audited against its exact historical plan and is neither reshaped nor retro-lit automatically, so an upgrade cannot overwrite a surviving or player-edited Bank.

Zero health during vanilla's revivable death animation is not removal proof. The entity must report actually removed before the following entity-inclusive save may create replacement authority; a zero-health entity saved during shutdown is restaged by its entity-load callback after restart.

## Village Prosperity split

Village Prosperity deliberately separates abstract simulation from physical materialization.

### Abstract simulation

Runs only against compact persisted records for known villages. It advances regardless of player distance and can catch up trusted time after the world was closed. It tracks population, housing, supplies, treasury, prosperity, safety, industry output, lifecycle, incidents, residents, and projects, but never loads chunks, runs villager AI, mines blocks, creates raids, or places structures.

### Physical materialization

Runs only in already-loaded chunks with nearby players, across the server's loaded dimensions. A known village is eligible when a player in the same dimension is within the configured horizontal X/Z radius; Y separation is intentionally ignored. The radius defaults to 256 blocks, accepts 48–512, and admits no more than 16 villages to one construction pass. Eligibility never loads a chunk. The physical layer performs censuses, tracks actual resident state, materializes all ten curated project types using one rotating global block budget, audits completed authored structures, and spawns pending settlers only when real housing, food, spawn-space, and safety requirements are met.

With visual progression enabled, a simulated population increase becomes a committed settler: it counts toward bounded economic population immediately, and the pending count records the entity still owed to the physical village. When a later census observes that villager, it transfers pending to physical population without changing the committed total. The deliberate exception is zero-population recovery, which remains economically inactive until real settlers appear.

Economic completion and physical completion are separate. An approved physical plan can reserve a safe lot, establish terrain supports, and reveal a bounded authored prefix while its labor phase advances. The materialized cursor cannot outrun economic progress, and the final block is withheld until economic completion. A completed economic plan becomes operational whether the village is loaded or nearby; its remaining physical template can stay safely queued. If an already materialized authored structure later fails integrity verification, its benefits are suspended. Partial damage remains in place for manual restoration. Severe demolition retires the old bounds and queues that same economic project at another safe site, with benefits still suspended until the replacement is complete. Thus unloaded or deferred visuals never stall simulation, while verified physical damage still matters.

## Authored village architecture and compatibility

New projects approved under format 18 use the immutable `blueprint_v2` contract. A village UUID deterministically selects one shared architectural character—Agrarian, Mercantile, Rustic, or Formal. The biome at the village's persisted center selects its material dialect—Plains, Desert, Savanna, Taiga, or Snowy—when the first physical lot is successfully reserved, and that dialect is then frozen for later projects. The result is controlled variety: buildings differ in shape and program while sharing a recognizable settlement language.

Blueprint V2 contains 52 whole-building gold masters across the ten project roles: six Cottages, six Houses, and five authored templates for every other role. Revision 2 is the active catalog. Its nine small, 18 medium, 14 large, and 11 landmark plans span distinct massing rather than repeating one envelope. Alongside the original masters, the catalog includes bay and courtyard cottages, a longhouse and orchard estate; hall, arcade, split-wing, and tower-court homes; wayfarer, coach-house, tavern, and courtyard inns; gabled, crane, wharf, and basilica warehouses; cruck, windmill, stilt, and silo-complex granaries; lane, hammer-hall, corner, and foundry smithies; adit, winding-house, drift, and quarry mines; crossroads, guild, lane, and bazaar markets; blockhouse, bastion, gatehouse, and citadel guard posts; and branch, counting-house, loggia, and monumental bourse exchanges. A template revision owns its floorplan, roof, frontage, circulation, support expectations, functional interior, and signature architectural details as one reviewed unit; those structural parts are never freely recombined. Small and medium plans are available from the beginning, large plans enter at tier 2, and landmarks enter at tier 4. Deterministic tier weights increasingly favor larger forms as a settlement develops, while a least-used per-scale shuffle bag prevents immediate template repetition whenever another candidate exists. Three semantic material palettes and three bounded dressing kits provide controlled surface and furnishing variation, and mirroring is possible only when the descriptor marks that exact revision safe.

Catalog admission renders every active master through every supported dialect, palette, dressing, and village character. It rejects dimension drift, overlapping construction stages, blocked circulation or workstation access, broken ladders and hatches, unsupported or disconnected roof components, half-slab weather gaps, orphaned panes, leaking enclosed rooms, concentrated token decoration, insufficient fixture spread, one-sided flush façades, missing architectural depth, flat one-feature rooflines, role-unreadable interiors, and a structural silhouette that is too close to another master. Role evidence comes only from the immutable base plan, so optional yard dressing cannot make a generic shell pass as a forge, mine, market, guard post, or exchange. This makes architectural detail and integrity production invariants rather than gallery-only polish.

Lighting admission evaluates the exact cumulative base, town, and city plans with skylight excluded. It derives every authored roof-covered floor whose state Minecraft accepts as Zombie-spawn support and whose two standing cells are clear, then propagates real block emission through conservative state-derived dampening. Every such floor must reach block light 7, rather than merely the spawn-safe minimum of 1. Attachment admission also runs against each cumulative plan and mirrors Minecraft 26.2: a standing lantern or torch needs a `SupportType.CENTER`-bearing face below it, every hanging lantern must follow a contiguous vertical chain (if present) to a `SupportType.CENTER`-bearing ceiling face, and a wall light needs a sturdy backing face in its authored facing direction. The same read-only gate admits each of the five current Bank dialect plans. The composer adds restrained supported pendants or wall fixtures when needed, and Bank validation applies the same lighting rule to the complete plan—including its roofed porch, apron, and three-wide landing—with a supported centered portico pendant.

The project persists its deterministic seed, template ID and revision, semantic palette, dressing kit, mirror choice, canonical signature, and versioned SHA-256 hash of the complete maximum-stage canonical placement stream. Lot selection later determines a stable connection target: the nearest eligible earlier project entrance when one exists, otherwise a settlement-edge hub. The authored north-facing entrance rotates by a persisted number of clockwise quarter turns to face that target. Architecture identity, rotation, biome dialect, anchor, visual stage, exact building bounds, building total, and the bounded terrain-matched entrance plan are committed before the first block is placed, so reload cannot reroll or reinterpret the structure.

Compatibility is deliberately one-way and non-destructive. Projects read from format 9 or earlier remain `legacy_v1` with their exact historical block order, origin, bounds, and cursor. Projects already saved by formats 10 through 17 remain `modular_v1` with their original seed, silhouette, roof, frontage, mirror state, and signature. Format-18 migration clears rather than invents Blueprint metadata for both older schemas; only a project approved after the current format is active receives `blueprint_v2`. Blueprint template revisions are independently immutable: new approvals select only the active revision-2 descriptors, but all 12 shipped revision-1 descriptors and their original envelopes remain resolvable so saved revision-1 projects resume from the same canonical plan. Retired revisions never re-enter selection and are not silently reshaped in place.

The base building, town stage, and city stage form append-only placement prefixes. A new project freezes the stage appropriate to its tier; a later rise preflights the complete new suffix, then atomically persists the higher target stage, total, and bounds before bounded construction resumes. A tier decline never removes a stage. Each layer receives deterministic shallow foundation columns down toward eligible natural support without mining through sound ground.

Prosperity roads are deliberately separate from the authoritative building plan. A road stores its frozen anchor, total, cursor, and completion flag, but its cells do not participate in project bounds, building totals, physical completion, integrity audits, or economic authority. Its deterministic plan is three blocks wide: one connected dirt-path/gravel primary lane plus both coarse-dirt shoulder lanes across segments, turns, and endpoints, with every cell inside the building envelope removed. Once its building is complete, a rotating scheduler advances the best-effort road only in already-loaded chunks. Existing TES-style path blocks are adopted; protected, occupied, fluid, obstructed, or non-terrain cells become gaps, and an unloaded cell waits without force-loading or starving every later road. A version-0 road retains the historical modular material selector until its frozen construction plan is complete, so no saved prefix is reinterpreted; current roads select the finished center material directly and never emit center coarse dirt. A separate one-time migration then freezes the exact historical coarse-center coordinate count and advances its own bounded cursor. Each advance is saved immediately, dirt path and gravel satisfy the scan, only surviving coarse dirt can be changed, and ordinary road totals/cursors—including inflated development-build totals—remain untouched.

The entrance approach is independent infrastructure persisted in format 15. The fixed top stair remains part of the immutable building template; a separate planner samples the first five frozen primary-road coordinates and accepts only a continuous descent of at most four additional stairs. It freezes a step count and a bounded ordered suffix containing bottom-up foundation supports, two air/headroom cells per stair, and inward-facing stair blocks. This suffix starts as soon as the building completes, before the longer road queue, and its cursor is saved after every successful pulse. Existing format-14 modular projects begin at version 0 and are planned once when loaded. If preflight finds an occupied, fluid, unloaded, or protection-vetoed coordinate it waits only for unloaded chunks; a genuine obstruction waives the entire unstarted retrofit. If a later obstruction appears after planning, the remaining suffix is permanently waived. Completed or waived approaches never run as a repair service, so player edits remain authoritative.

## Village configuration modes

The following settings are independent:

```properties
village_prosperity.simulation_enabled=true
village_prosperity.visual_progression_enabled=true
village_prosperity.market_integration_enabled=true
village_prosperity.automatic_recovery_enabled=true
```

`simulation_enabled` controls abstract local-economy advancement. `visual_progression_enabled` controls settlement materialization. `market_integration_enabled` controls whether eligible settlement fundamentals affect asset drift and commodity supply. `automatic_recovery_enabled` controls automatic recovery from eligible extinction.

## Construction safety

Prosperity projects are intentionally conservative:

- No forced chunks. Passing the horizontal activation-radius check is only permission to inspect already-loaded world state.
- A project's first deterministic sweep inspects 64 candidates through 84 blocks. Each fully failed sweep persists backoff and unlocks another bounded 24-site ring, up to 256 candidates through 276 blocks; due projects rotate between pulses so one difficult frontier cannot starve later work. Bank searches retain their separate 48-candidate, 82-block bound. Neither search force-loads chunks.
- Candidate lots must be already loaded, naturally surfaced, and within the supported four-block foundation range. Project preflight transforms the authored base first, then proves every authoritative ground-contact column—including rotated or mirrored annexes outside the nominal descriptor—terminates on loaded natural ground. A Bank's three entrance lanes must resolve to the same bounded stair plan, while every physical prosperity lot must resolve a continuous center approach along its frozen road route before reservation.
- The ground must match a small natural-ground whitelist.
- Mud and thin snow layers are not structural Bank support; full snow blocks remain eligible natural ground.
- The project floor is placed in air above the existing terrain surface.
- Block entities, solid construction, paths, farmland, and protection-claimed cells are not replaced. Replaceable vegetation and snow may be cleared, and best-effort roads may pave only dirt-like or sandy ground; stone-family, snow, and every other non-soil block are skipped. Because vanilla block state has no player-placement provenance, a claim guard is still required to protect player-placed dirt, grass, podzol, mycelium, or sand from that narrow soil-paving behavior.
- Both prosperity projects and Village Banks consult `VillageDevelopmentProtection.register(PlacementGuard)` before placement. Integrations have no mandatory claim-mod dependency; a registered veto or thrown guard exception denies the placement.
- A block advances project progress only when Minecraft accepts the placement and the resulting state matches the authored template.
- Unsafe candidates are rejected before reservation so the bounded search can try another lot. An unloaded project frontier also records persistent backoff before the next expanded sweep, allowing another due project to advance without force-loading the frontier. After a reservation is persisted, any ordinary later obstruction or unloaded boundary uses persistent exponential retry backoff and retains the exact site—even at a recorded zero prefix. A block that reaches a chunk save before its cursor is journaled is safely adopted on the next idempotent pulse. The reverse process-crash ordering remains an explicit limit below.
- Partially built projects retain their exact persisted bounds and deterministic recipe prefix, then retry in place without clearing or overwriting intervening player work.
- A failed Bank candidate write remains unmarked and creates no untracked Banker, allowing a later clean retry without claiming an uncertain mutation. A scan with no proven candidate, including an incomplete loaded-chunk scan, first records explicit Banker-only provenance and only then adopts or spawns its canonical Banker, so that lifecycle survives restart and cannot duplicate merely because the entity unloads. Nearby players within 192 horizontal blocks keep that known fallback active even outside the vanilla POI boundary and even if its old center chunk unloads; one shared bounded recovery pass considers at most four due villages per scan, expands from the ordinary 48 sites/82 blocks to 96 sites/128 blocks, prefers fully outside-village lots nearest-first, and never force-loads a candidate. Completing the structure durably clears fallback provenance and reuses the canonical scoped Banker. Formats 10 and earlier remain unknown and non-retryable, so ambiguous legacy, damaged, or crash-interrupted Bank anchors are never guessed at or rebuilt. Replaceable vegetation is accepted during lot clearance, but solid blocks and block entities remain protected. Rollback matches authored block identity so neighbor-updated pane and fence states are included.
- An unversioned existing Bank is upgraded only when its persisted anchor and recognized bank workstation (Exchange Desk or scoped legacy lectern), counter, doorway, threshold, roof mount, and hanging-lantern signature identify the supported 13x11 design. The whole entrance suffix must be loaded, dry, unobstructed, accepted by every protection guard, and resolve to the same stair rows in all three independently sampled lanes before placement begins. Only air or replaceable cells are changed. The retrofit defers while saving is disabled, runs Minecraft's synchronous chunk-save barrier before recording version 2, and paces failed retries; a failed placement, thrown barrier error, or structure-version save rolls the new cells back. A normal barrier return improves write ordering but does not make Minecraft chunk files and the economy file one transaction. Missing or player-replaced furnishings and panes are never inferred as Bank ownership.

Cottages include real beds. Warehouses use chests instead of barrels so they do not unintentionally create fisherman workstations.

Active resident professions contribute bounded sector multipliers to abstract production. During nearby construction, at most two suitable villagers periodically receive a one-shot low-speed route toward a safe exterior waypoint, look, swing, and emit particles near the project. Entity queries and route eligibility remain capped at the local 48-block range even when the development radius is configured to 256 or 512; a new settler's assigned home radius is separately capped at 32 blocks. These effects are deliberately non-authoritative theatre: they install no persistent AI goal and do not control economic progress.

A low-frequency integrity pass checks one physically completed authored project at a time, and versioned generated Banks receive the same read-only structural decision. Any authored mismatch suspends the building: a partial edit is marked unsafe and is never repaired, overwritten, or duplicated, while restoring the complete authored structure lets a later audit reactivate it. Authored project doors and workstations remain structural authority, while nonessential base decoration is deliberately cosmetic and cannot trigger repair or relocation. Reserved air, entrance standing space, access targets, and vertical-access dismounts are strict semantic clearances: a player block there makes the building unsafe but is never removed or overwritten, and that access-only obstruction does not count as severe structural demolition. Bank-only outdoor clearance keeps its existing tolerance for safe replaceable, dry, block-entity-free growth. A scoped Banker remains fail-closed while its active Bank is unsafe, but a surviving Exchange Desk there opens unscoped personal banking so structural state cannot strand player finances. Only severe demolition—at least 12 mismatches and at least 30 percent of authored structure cells—can retire a site and queue a replacement elsewhere. The old blocks remain untouched. Its exact project bounds or Bank anchor enter a bounded append-only history, every later search excludes every retained site, and an Exchange Desk at a retired coordinate is no longer a valid access point. Each project and Bank region retains at most 16 retired entries; once full, further damage remains unsafe rather than discarding an older exclusion. Append-only legacy-template and modular design-stage upgrades use the ordinary loaded-chunk, collision, and protection rules. Solid construction, block entities, protected placements, and unloaded chunks are never overwritten or force-loaded. Modular road cells are excluded from this audit because they are public, best-effort infrastructure rather than building authority.

Blueprint V2 light emitters needed by that admission gate are runtime structural authority even when their authored stage is decorative. Their complete attachment closure is derived from the cumulative base-plus-stage map, so a hanging lantern keeps every intervening chain and its terminal beam across phase boundaries; standing and wall-mounted lights likewise keep their required support. This promotion changes neither raw authored geometry nor the canonical plan hash. If a player removes or replaces a required fixture or support, the project becomes unsafe and manual-restoration-required; the mod never recreates the cell. A versioned Bank applies the same fail-closed, no-repair rule to its authored lights and supports.

One cross-file durability limit remains explicit. Bank markers and project cursors live in the economy save while structure blocks live in Minecraft chunks; those writes are not atomic together. Rare Bank build and upgrade paths use a synchronous world-first barrier, and a marker failure performs and saves a best-effort rollback, but Minecraft cannot expose one transaction spanning both files. Incremental projects deliberately do not force a global chunk save every two-block pulse. A crash can therefore leave a non-provenanced Bank marker without a structure, or a project cursor ahead of a lost chunk write. The mod uses an eligible fallback Banker for the former and conservatively classifies the latter as damage rather than auto-repairing a block that a player may have removed.

## Resident lifecycle

Resident records track Active, Away, Infected, Emigrated, and Dead states. Missing entities are never inferred dead.

- Active residents absent from repeated loaded censuses become Away after a grace period.
- Residents still absent after the longer emigration window become Emigrated and stop contributing to productive population.
- Zombie villagers are reconciled to nearby or tagged residents and recorded as Infected, suspending productive population without inventing a death.
- A living villager later observed near an infection can reconcile the stale infected record as a cure.
- Explicit villager death events create casualties and lifecycle incidents.

Direct player and player-owned projectile kills are marked player-caused when Minecraft exposes ownership. Environmental traps without attacker attribution remain environmental incidents.

Before the first player-caused casualty mutates an eligible settlement, the service persists both the exact live village state and its current market contribution. This becomes a no-player-damage counterfactual branch, not a static score: on each economic day with Village Prosperity simulation enabled, it runs the normal abstract village simulation without applying the player's damage, then recalculates its eligibility, aggregation weight, and sector contributions. Genuine non-player casualties observed while the branch is active are applied to the counterfactual and immediately re-priced. Further player hits can extend the cooldown but never recapture or rebase the branch.

Market aggregation uses the counterfactual result until the cooldown has elapsed, the live village is Active again, and its population has returned to at least the captured level. Other settlements continue normally. Live-only changes that are not part of the no-player-damage branch do not rewrite its history before release.

A Threatened or Devastated settlement with one or two living survivors can transition to Recovering after the seven-day stabilization window once safety and prosperity reach the recovery floor. This restores access to bounded population growth without applying the zero-population automatic-refugee rules.

## World state

The economy is global to one Minecraft world or dedicated server. Market prices and regimes are shared by all players. Player accounts and pending inventory transactions are keyed by UUID. Village records are keyed by their persistent settlement UUID.

The economy seed is generated from secure random data on first creation, mixed with world information, and stored privately. It is not predictable solely from the visible Minecraft world seed.

## Unified economic clock

The current save stores wall-clock time, server game ticks, and one pending economic-millisecond accumulator. The save also stores the last observed baseline for the commandable Overworld clock. For each observation, the largest forward delta among trusted wall time, server game time, and the Overworld clock is added once. This supports offline catch-up and `/time` command acceleration while preventing overlapping clocks from being counted twice. Backward Overworld-clock movement only rebases the persisted baseline. Older saves without that field initialize it from the live world once; afterward startup compares the live clock with the persisted observation so a Minecraft-saved command jump cannot be lost before the next economy tick.

One economic day equals 1,200,000 milliseconds. Startup advances at most 2,000 economic days before the server opens. Remaining catch-up is processed in bounded batches and banking pauses until the market is current.

## Currency precision and no-debt invariant

One emerald equals 1,000,000 micro-emeralds. Cash, savings, CDs, villager lending, inventory-journal deltas, commodity proceeds, cost basis, and Prosperity Fund balances use integer micro-emerald values. Shares remain validated finite nonnegative doubles in the current beta.

No player account contains a debt balance. A Prosperity Fund contribution is an irreversible gift to a village-owned balance, not borrowing or a player investment, and a player can never owe more emeralds than were voluntarily committed.

## Persistent data format 18

Format 18 includes:

- Required magic identifier and explicit format number
- SHA-256 checksum over sorted state properties
- Global market, commodities, regime, event, and up to five years of asset and commodity history
- Unified economic-clock state
- Bank regions, active anchors, bounded append-only retired-anchor histories, one canonical Banker UUID and last durably assigned anchor per generated region, entity-removal-ordered death tombstones, exact typed pending conversion transactions, explicit Banker-only fallback provenance, and positive authored structure versions for anchored non-fallback generated Banks
- Player accounts, up to eight independently identified CDs and eight lending positions, holdings, share cost basis, realized gain, contribution and withdrawal totals, a bounded transaction ledger, personal net-worth history, and pending inventory transactions
- Village-owned Prosperity Fund purpose balances, source-aware fast-track eligibility, protected endowment principal, project sponsorships, emergency reserves, bounded contribution records, and global donor recognition
- Stable village identities and bank associations
- Village lifecycle, resident records, incidents, resources, production, tier, restoration state, and pending settlers
- Per-village no-player-damage counterfactual state, its daily re-priced market contribution and weight, and its capture/release metadata
- Project approval, economic completion, site reservation, exact active bounds, physical progress, retry deadline, materialization-failure count, relocation-pending state, and bounded append-only retired-lot histories
- Per-village architectural character and frozen biome dialect
- Per-project architecture schema and deterministic seed; historical modular silhouette, roof, and frontage fields; Blueprint template ID and revision, semantic palette, dressing kit, mirror flag, canonical signature, plan-hash version and SHA-256 plan hash; road-facing rotation; and frozen visual stage
- A frozen road anchor plus an independent road total, cursor, and completion flag
- A per-project center-surface migration version plus a frozen bounded target and independent cursor
- A per-project entrance-approach version, frozen step and placement totals, independent cursor, and completion flag

The 0.4 line accepts its earlier supported save formats and writes them forward as format 18. Format 8 introduced the expanded project catalog; format 9 added multi-position term products, portfolio accounting, commodity and personal history, Prosperity Funds, and donor records; format 10 added the modular architecture contract and separate road state; format 11 added explicit Banker-only fallback provenance; format 12 added the independent Bank structure-version map; format 13 added relocation-pending state, retired project-lot and Bank-anchor histories, and canonical generated-Banker UUIDs; format 14 added the independent one-time modular-road center-surface migration; format 15 added the independently frozen entrance approach; format 16 added generated-Banker death tombstones; format 17 added typed conversion transactions and entity-removal-first death authority; and format 18 adds immutable Blueprint V2 selections and versioned canonical plan hashes.

Eligible physical modular roads from format 13 and earlier begin at migration version 0 with an uninitialized scan target; eligible format-14 modular approaches begin at version 0 with no trusted target, while legacy, abstract, and unreserved projects remain ineligible and unchanged. Each exact target count is saved before its first world write, and road resurfacing waits for the ordinary frozen road to complete. Format-12 input cannot supply trusted values for the format-13 ownership-sensitive fields: migration initializes them empty rather than accepting similarly named properties. Format-14 input likewise cannot supply trusted format-15 entrance fields, and format-15 input cannot supply trusted format-16 death tombstones. Format-16 death tombstones predate the entity-removal barrier and are deliberately dropped during migration instead of being trusted as duplicate-creating replacement authority; a genuinely dead Banker from that unpublished candidate may require manual recovery. Format-17 input cannot supply trusted format-18 Blueprint identity or plan hashes, so migration leaves those fields empty and retains every existing `legacy_v1` or `modular_v1` project exactly. Bank markers read from format 11 or earlier acquire no trusted structure version, even if an older file contains an unknown similarly named property; a live exact-signature check, guarded upgrade, and chunk-save-before-marker ordering are required before version 2 is recorded. Bank markers read from formats 10 and earlier also remain non-retryable when their anchor matches a village center, because older real Banks and fallbacks cannot be distinguished safely. Legacy scalar CD and lending products are promoted into identified position collections, and holdings without execution history receive an explicitly inferred basis at the migration-day market price. Older builds reject format 18 as a future format without stale-backup fallback. Downgrading therefore requires restoring a pre-upgrade world backup. Unsupported formats newer than 18 are likewise rejected without overwriting them.

## Save process

Writes validate complete state and no-debt invariants, serialize mandatory fields, calculate the checksum, flush a temporary file, preserve a validated previous save as `.bak`, atomically replace the primary when supported, and best-effort flush parent directory metadata.

Inventory-linked deposits, withdrawals, and exchanges use durable `PREPARED` and `BANK_COMMITTED` journal stages because Minecraft player inventory and the bank are stored separately. See [TRANSACTION_RECOVERY.md](TRANSACTION_RECOVERY.md).

## Current beta scaling boundary

An in-memory, rebuildable spatial index divides villages into 64-block X/Z cells and per-dimension buckets. Nearest-village identity lookups retain exact three-dimensional distance filtering and deterministic legacy tie behavior. Multi-origin `villageSnapshotsNear` queries serve physical-development activation and therefore apply same-dimension horizontal X/Z eligibility so altitude cannot deactivate an otherwise local settlement. Both paths use a bounded fallback when a requested radius would require too many cells. The index is rebuilt on world load and updated after a successful new-village observation; it is not additional persisted state.

Catch-up batches scale down with known account and settlement counts. Physical development remains restricted to dimension-matching villages within the configured horizontal radius of loaded players, considers at most 16 eligible villages per pass, and performs world work only in chunks already loaded by Minecraft. Snapshot lists reuse one village-fundamentals calculation. Regression measurements cover lookup correctness plus query, save, and load work at 100, 500, and 1,000 villages and accounts.

The simulation is intentionally lightweight for single-player and ordinary multiplayer, but very large public servers will eventually need storage partitioning. Ordinary mutations still synchronously serialize the whole shared world economy file, so persistence work remains linear in world state. A player-only sidecar or write-behind path is not used because global day, price, and village changes must not be acknowledged before they are durably saved together.


## Debug flight recorder

`DebugFlightRecorder` is a server-side, operator-triggered, time-bounded diagnostic layer. Loader tick hooks perform only a constant-time inactive lookup when no capture exists. During a capture, the recorder samples the authoritative `EconomyService`, the initiating tester's account, and one watched nearby settlement; instrumentation hooks add only that settlement's construction, census, casualty, settler, and GUI-action events. The initiating operator owns mark, toggle, and stop controls.

The JSON Lines timeline is flushed after every event and packaged with sanitized snapshots at normal stop, timeout, disconnect, size limit, or server shutdown. Any `.active-*` directory left by a process crash is converted into an `INCOMPLETE-CRASH` report during the next initialization. The recorder never serializes the private economy seed, resident identities, or unrelated player and settlement data. Sampling, recorder-tick, write, snapshot, and full-copy timings are labeled separately and may overlap; they are diagnostic costs, not a Minecraft subsystem profile.
